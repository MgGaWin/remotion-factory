# 信息/科普解释模式

用于非叙事抒情类视频：科普、技术讲解、代码项目讲解、产品原理、数据报告、教程、观点分析、机制解释。目标是先把内容讲清楚，再把它做成视频。

## 何时启用

默认启用条件：

- 用户给的是简略文章、提纲、观点草稿，但希望做成信息类视频。
- 用户同时给了文章和代码项目、论文、文档、数据、截图等支撑材料。
- 内容属于“解释一个东西为什么成立 / 怎么工作 / 怎么使用 / 有什么取舍”。
- 原文信息不足，直接改写会变成空泛口播。

不默认启用：

- 抒情散文、信件、回忆录、品牌故事等以情绪和叙事节奏为核心的内容。
- 用户明确要求只忠实朗读原文，不扩展解释。

## 核心原则

- 不是摘要器，是解释器。
- 不是把内容变长，而是补齐理解链条。
- 每个知识点必须回答：是什么、为什么、怎么证明、边界在哪、观众该记住什么。
- 扩展内容必须来自用户材料、代码项目、可验证常识或明确标注的推理；不要编造数据、引用、案例。

## Phase 1 新增产物

启用本模式时，Phase 1 先产出：

```text
feynman-notes.md
script.md
outline.md
```

其中 `feynman-notes.md` 是口播稿之前的解释草稿，用来暴露缺口。

**质检衔接**：`feynman-notes.md` 产出后，必须经过 Checkpoint Plan 的 Agent 1（内容质检）检查。Agent 1 会读取 `feynman-notes.md`，验证每个概念是否包含完整的费曼结构字段（一句话解释、新人类比、为什么需要、证据来源、常见误解、Payoff 句）。质检不通过则必须修复后才能进入 script.md 编写。

## 费曼扩写流程

> **费曼扩写的双重价值：** 费曼扩写不仅产出观众能理解的内容，更让使用者自己在拆解、重组、扩写概念的过程中建立更深的理解。当你能把一个复杂概念用大白话讲清楚时，说明你真正理解了它。这就是"教是最好的学"——使用者在创作视频的过程中，自己也在成长。

### 1. 抽主线

从文章或提纲里提取：

- 目标观众：完全新手、有基础但不了解该项目、专业观众、决策者等。
- 核心问题：这期视频到底帮观众解决什么疑问？
- 结束收益：看完后观众能解释、判断、操作或避免什么？
- 必讲概念：不能省略的定义、机制、步骤、对比、限制。
- 不能擅自扩展的边界：没有来源的数据、未给出的性能结论、主观营销表述。

### 2. 读支撑材料

如果有代码项目，先找：

- `README`、`package.json`、入口文件、示例、测试、核心目录。
- 主流程：请求/数据/命令从哪里进，经过哪些模块，到哪里输出。
- 关键函数/类：能证明文章观点的真实实现。
- 配置和边界：默认值、错误处理、性能/安全/兼容限制。

如果有论文/文档/数据，先找：

- 结论、方法、证据、实验或案例。
- 术语定义和适用条件。
- 数据来源、口径、统计时间。
- 原文没有说清楚但观众会自然追问的点。

### 3. 逐点费曼化

每个知识点按这个结构写入 `feynman-notes.md`：

```markdown
## 概念/问题：xxx

- 一句话解释：
- 新人类比：
- 为什么需要它：
- 如果没有它会怎样：
- 证据/项目位置：
- 关键代码/数据/案例：
- 常见误解：
- 边界条件：
- 解释层级：L1 / L2 / L3
- 视频里的 Payoff 句：
```

**解释层级（L1 / L2 / L3）**：同一个概念在视频里往往需要分多次出场——先给直觉，再给细节，最后给结论。为每个概念标注层级，后续 `outline.md` 按层级分配场景：

| 层级 | 含义 | 信息量 | 对应帧型 | 回答「这是什么」还是「为什么这样」 |
|------|------|--------|----------|----------------------------------|
| L1 直觉层 | 一句话大白话 + 类比 | 最低 | 简洁帧 / 章节开场 | 这是什么，能干什么 |
| L2 机制层 | 拆解原理、步骤、代码 | 中高 | 密集帧 D1-D6 | 为什么成立、怎么运作 |
| L3 深挖层 | 边界、反例、常见误解 | 最高 | 密集帧 / Feature 暗卡 | 什么时候不成立、容易错在哪 |

**L1 到 L3 是递进的**：L1 不完整没关系，观众需要先有锚点才能接住 L2 的细节。L3 的边界和反例是区分「真正理解」和「表面知道」的分水岭，不要跳过。

每条概念至少标注 L1+L2，重要概念标满三层。直接在 feynman-notes.md 里为同一个概念拆成三个条目，不要合并。

**证据来源分类**：

证据字段按内容类型采用不同标准，不能所有知识点都用同一句话「原文第 X 段」敷衍：

| 内容类型 | 证据要求 | 示例标注 |
|---------|---------|---------|
| 代码项目 | 精确到文件路径 + 函数/类名 | `src/core/scheduler.ts:142 scheduleTask()` |
| 学术论文 | 精确到章节/图表编号 | `Figure 3 / Section 4.2` |
| 文档/Spec | 精确到章节或 URL | `RFC 8446 Section 4.2.2` |
| 数据/报告 | 标注来源、口径、统计时间 | `2024Q4 财报 p.12，Non-GAAP，同比增速` |
| 概念科普（原文可验证） | 精确到原文段落 | `article.md 第 4 段「状态更新的批量处理」` |
| 概念科普（无原文来源） | 明确标注为推理，且必须是可验证常识 | `⚠ 推理：基于 React 18 并发特性的一般性推断，非原文确认` |

**硬规则**：无法标注为以上任一类的断言，不得写入 feynman-notes.md。宁可标记「需要用户确认」，不可编造。



### 3.1 类比构造指南

类比是费曼技巧中最强大的武器，但坏类比比没有类比更糟。每个「新人类比」必须满足以下规则：

**好类比的三条硬标准：**

1. **保留核心机制**：类比必须平行映射原概念的关键因果链，不能只映射表面特征。
   - 好：「异步」类比成「餐厅点餐后不等在柜台，先坐下，菜好了叫你」——保留了「不阻塞 / 回调通知」的核心机制。
   - 坏：「异步」类比成「快递」——只映射了「不即时」，丢了「事件循环 / 回调」的关键结构。

2. **指明类比边界**：明确说出「这个类比在 XX 方面不成立」。
   示例：「可以先把 Vector Database 理解成图书馆的索引卡片——但你不需要知道书在哪一层，只需要索引指向内容。不过和图书馆不同的是，向量检索是近似匹配而不是精确查找，所以结果可能不是 100% 准确。」

3. **用观众熟悉的领域做类比**：非技术观众用日常经验（烹饪、交通、购物），技术观众可以用其他技术栈。禁止用一个技术概念类比另一个技术概念给非技术观众。

**禁止的类比模式：**
- 「就像 XX 一样」然后不再展开——零信息量
- 用更复杂的概念类比简单概念——反向混淆
- 类比涉及观众不熟悉的文化/地域常识——产生新困惑

### 4. 找解释缺口

标出这些问题：

- 术语突然出现，没有定义。
- 只讲怎么做，没有讲为什么。
- 只讲优点，没有讲边界或代价。
- 代码细节很多，但没有主流程。
- 结论和证据之间缺桥梁。
- 观众不知道这一段和自己有什么关系。

缺口能从材料中补，就补进 `feynman-notes.md`；不能补，就在 notes 里标记“需要用户确认”。

### 5. 生成口播稿

从 `feynman-notes.md` 生成 `script.md`。口播要像老师讲课，不像百科条目：

- 先抛问题，再给解释。
- 先用大白话，再给准确定义。
- 先讲主流程，再讲局部代码。
- 每 60-90 秒用一句话回收。
- 每个概念都要有 Payoff 句。

推荐句式：

```text
你可以先把它理解成……
真正关键的是……
如果没有这一步，会发生什么？
我们回到项目里看这段代码……
这里容易误解成……
所以这一节只需要记住一句话……
```

## 防止泛泛而谈

### 什么是泛泛而谈

泛泛而谈是指用未经展开的概括性表述代替具体信息，导致读者听完后无法复述、无法行动、无法验证。它看起来"说了什么"，实际上什么都没说。

### 检测词汇表

扫描 script.md，标记以下词汇——这些词出现时，必须展开或删除：

| 词汇 | 问题 | 展开方式 |
|------|------|----------|
| 等等 | 暗示有更多但没说 | 列出具体的 2-3 项 |
| 诸如此类 | 模糊列举 | 给出具体例子 |
| 就不展开了 | 跳过了关键内容 | 要么展开，要么删除整句 |
| 大家可以自行了解 | 把责任推给观众 | 在视频里讲清楚 |
| 本质上 | 用抽象词代替解释 | 用具体机制替代 |
| 简单来说 | 可能过度简化 | 确保简化后不丢信息 |
| 基本上 | 模糊限定 | 给出具体条件 |
| 一般来说 | 暗示有例外但没说 | 说明具体条件和例外 |
| 某种程度上 | 模糊程度 | 给出具体数据或比例 |
| 众所周知 | 假设观众已知 | 从零开始解释 |
| 不言而喻 | 跳过了解释 | 显式说明 |
| 很重要 | 无信息量 | 说明为什么重要、解决什么问题 |
| 有很多优点 | 空洞列举 | 列出具体 2-3 个优点并说明解决什么问题 |
| 广泛使用 | 模糊范围 | 列出具体使用场景 |
| 性能更好 | 无比较基准 | 说明比什么好、好多少、用什么指标 |

### 替换策略

| 泛泛而谈 | 具体化改写 |
|---------|-----------|
| "很重要" | "解决了 XX 问题，没有它会 YY" |
| "有很多优点" | "三个优点：1)... 2)... 3)..." |
| "广泛使用" | "在 A 场景用因为 XX，在 B 场景用因为 YY" |
| "性能更好" | "比 XX 快 3 倍，因为采用了 YY 策略" |
| "大家都知道" | 直接删除，从零开始解释 |
| "底层实现" | 贴出关键代码片段 |
| "很多公司" | "Netflix、Spotify、Airbnb" |
| "很快" | "200ms 内" |

### 质检规则

- script.md 中出现检测词汇表中的词 → 标记为"需具体化"
- 超过 3 处未展开的泛泛而谈 → 内容质检 FAIL
- 每个标记处必须有具体解释或删除

### Payoff 句好坏示例

**坏示例**（无信息量，不可复述）：
- "总之，这个技术很重要。"
- "所以大家要记住这个概念。"
- "这就是今天的内容，希望对你有帮助。"

**好示例**（可复述、有边界、有场景）：
- "所以你只需要记住：React 的状态更新是异步的，这意味着在同一个事件处理函数里连续调用两次 setState，视图只会刷新一次。"
- "RAG 的核心思路就一句话：先从知识库里找到相关文档，再让模型基于这些文档生成回答——这样模型就不会编造它不知道的信息。"
- "自定义 Hook 的本质，就是把状态逻辑变成可复用的函数——就像把一段常用的 CSS 抽成 class 一样。"

**判断标准**：好的 Payoff 句应该让观众在不看视频的情况下，仅凭这句话就能向别人解释核心概念。

## 内容类型模板

### 概念科普

结构：

```text
观众疑问 → 直觉类比 → 准确定义 → 机制拆解 → 例子 → 常见误解 → 一句话总结
```

适合：AI 概念、协议、框架、科学现象、商业概念。

### 机制/原理解释

结构：

```text
现象 → 反直觉点 → 简化模型 → 真实机制 → 证据 → 边界 → 影响
```

适合：模型原理、系统架构、算法流程、自然科学机制。

### 代码项目讲解

结构：

```text
用户问题 → 项目解决思路 → 架构心智模型 → 主流程 → 关键模块 → 代码证据 → 取舍/限制 → 可复述总结
```

场景映射：

- 架构心智模型：简洁帧或 D2 左文右数据。
- 主流程：D3 编号列表或流程图式密集帧。
- 关键模块：D4 左解释+右代码。
- 取舍/限制：D6 问题-改进对比。
- 总结：Feature 暗卡或简洁 Payoff 帧。

### 教程/操作指南

结构：

```text
目标结果 → 前置条件 → 步骤 → 每步为什么 → 验证方法 → 常见错误 → 下一步
```

每个步骤必须包含“怎么判断做对了”。

### 数据/报告解读

结构：

```text
一句结论 → 指标定义 → 关键趋势 → 可能原因 → 证据 → 反例/限制 → 行动建议
```

不要只念数据。先说“这组数据说明什么”，再解释数据。

### 观点/分析类

结构：

```text
观点 → 判断标准 → 证据 1/2/3 → 反方可能意见 → 适用边界 → 结论
```

观点类必须分清“事实、推理、判断”。不要把判断说成事实。

## outline.md 增强要求

启用本模式时，`outline.md` 每个场景必须额外标注：

```markdown
- Scene X: 场景名称
  - 解释单元：概念 / 机制 / 代码证据 / 对比 / 总结
  - 解释层级：来自 feynman-notes.md 的 L1/L2/L3
  - 观众问题：这一屏回答哪个具体疑问？
  - 证据来源：article.md / feynman-notes.md / 代码路径 / 数据来源（按证据分类标准标注）
  - Payoff 句：观众应该记住的一句话
  - 帧型：简洁帧 / 密集帧 D1-D6
  - 视觉重音：Level 1-5
```

### 观众问题质量标准

「观众问题」不是随便写一句「什么是 XX」。好问题满足三个条件：

1. **具体**：不是「什么是异步」，而是「为什么异步操作不会卡住页面」
2. **前置**：写在观众嘴里还说不出来、看完这屏能脱口回答的那句话的反面
3. **制造好奇**：暗示答案不重要但反直觉

坏问题（禁止）：
- 「什么是 React？」——太宽泛，一屏回答不了
- 「XX 的优点是什么？」——像考试题，不是真疑问
- 「为什么要用 XX？」——没有给出怀疑的理由

好问题（推荐）：
- 「React 怎么做到只更新变化的部分，而不是整个页面重刷？」——具体、可回答
- 「RAG 和直接用大模型回答有什么区别？为什么不能直接让模型自己搜？」——对比制造好奇
- 「langGraph 里节点和边到底代表什么？和普通流程图有什么不一样？」——和已有知识锚定

**判断标准**：如果观众看到这屏画面的第一秒，心里正好浮现你写的这个问题，那这个问题就写对了。


## 质量闸门

生成 `script.md` 前先自检：

- [ ] 每个核心概念都有大白话解释。
- [ ] 每个核心概念都有“为什么需要”。
- [ ] 每个重要结论都有证据来源。
- [ ] 代码项目讲解没有只讲文件名，而是讲清主流程。
- [ ] 没有编造数据、案例、用户反馈或论文结论。
- [ ] 没有把不确定推理写成确定事实。
- [ ] 每 60-90 秒至少有一句 Payoff 句。
- [ ] 口播中术语第一次出现时有解释。
- [ ] `outline.md` 能追溯每个场景的证据来源。
